<objective>
Die Service-Schicht für das Urlaubs-Journal: Buchungen schreiben, Journal lesen, Saldo aus
Buchungen berechnen.

Zweck: Ein einziger, getesteter Zugriffspunkt auf das Journal. Alle späteren Schreibpfade
(Phase 6) und Ansichten (Phase 8) gehen ausschließlich hierüber — nicht mit eigenen SQL-Queries.
Genau diese Streuung von Buchungslogik über mehrere Services hat den ursprünglichen Fehler
möglich gemacht.

Ergebnis: Getestete Funktionen, die noch von niemandem aufgerufen werden. Verhalten weiterhin
unverändert.
</objective>

  <files>server/src/services/vacationTransactionService.ts</files>

  <steps>
1. `getVacationBalanceFromTransactions(userId, year): number`
   → `SELECT COALESCE(SUM(days), 0) FROM vacation_transactions WHERE userId = ? AND year = ?`
   Auf 2 Nachkommastellen runden (wie `getOvertimeBalance`), da Urlaub in halben Tagen geführt wird.

2. `getVacationTransactions(userId, options?): VacationTransaction[]`
   Optional filterbar nach `year`, mit Limit. Sortierung: `date ASC, id ASC` — die Reihenfolge
   muss stabil sein, damit der Kontoauszug in Phase 8 einen nachvollziehbaren laufenden Saldo
   zeigt. `id` als Sekundärschlüssel, weil mehrere Buchungen dasselbe Datum tragen können.

3. `getVacationTransactionsForAbsence(absenceId): VacationTransaction[]`
   → alle Buchungen zu einem Antrag, über `referenceType='absence' AND referenceId=?`.
   Wird in Phase 8 für die Verlinkung und in Phase 7 vom Konsistenzprüfer gebraucht.
  </steps>

<task type="auto">
  <name>Task 3: Buchungsfunktion</name>
  <files>server/src/services/vacationTransactionService.ts</files>

  <steps>
1. `recordVacationTransaction(input): number` — **synchron**, gibt die neue `id` zurück.

   Eingabe: `userId`, `year`, `date`, `type`, `days`, `description`, `createdBy`,
   optional `referenceType` + `referenceId`.

2. `balanceBefore` innerhalb der Funktion aus `getVacationBalanceFromTransactions()` ermitteln,
   `balanceAfter = balanceBefore + days`. Beide Werte mitschreiben.

   Damit trägt jede Zeile ihren eigenen Nachweis — der Kontoauszug kann später ohne Nachrechnen
   angezeigt werden, und eine gebrochene Kette fällt sofort auf.

3. Pflichtprüfungen, die eine unbrauchbare Buchung gar nicht erst entstehen lassen:
   - `days` ist eine endliche Zahl und nicht 0 → sonst werfen
   - `description` ist nicht leer (REQ-04) → sonst werfen
   - `type` ist einer der sechs erlaubten Werte
   - `year` liegt zwischen 2000 und 2100

4. Kein `async`, kein `await`, kein dynamischer Import in dieser Funktion.
  </steps>

  <verify>
```bash

```
