<objective>
Eine Admin-Korrektur am Urlaubskonto bekommt endlich ihre Begründung — aus der Oberfläche heraus.

Zweck: Phase 6 hat serverseitig durchgesetzt, dass eine Kontoänderung eine `correction`-Buchung
erzeugt, und hat eine leere Begründung abgewiesen. Der Admin-Dialog sendet das Feld `reason`
aber gar nicht — der Server greift deshalb auf einen Ersatztext zurück. Im Kontoauszug steht
damit eine Buchung ohne Aussage, und genau darin lag die ursprüngliche Schwäche des Systems:
eine Bewegung, die niemand erklären kann.

Ergebnis: `VacationBalanceEditModal` verlangt eine Begründung, reicht sie an
`POST /api/vacation-balances` durch, und der Kontoauszug aktualisiert sich danach von selbst.

Abgrenzung: Der Serververtrag wird **nicht** verschärft. Die Übergangsregel aus Phase 6
(fehlendes Feld → Ersatztext, leeres Feld → 400) bleibt unverändert; das Verschärfen des
Servers gehört zu REQ-06 und damit zu Phase 6.
</objective>

POST /api/vacation-balances
  Body: { userId: number, year: number, entitlement: number, carryover: number, reason?: string }

  - `reason` als leere Zeichenkette → 400 mit
    'Eine Begründung ist erforderlich, wenn das Feld reason gesendet wird — leere Zeichenkette ist nicht erlaubt.'
  - `reason` fehlt vollständig → der Server setzt einen Ersatztext (Übergangsregel Phase 6)
  - `reason` gesetzt → wird zur `description` der `correction`-Buchung und erscheint so im
    Kontoauszug
