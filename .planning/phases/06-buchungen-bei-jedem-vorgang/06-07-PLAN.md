**Was korrigiert wird:** Karin Jochem (userId 2) und Christine Glas (userId 3) haben beide

bei beiden einen vollen Jahresanspruch, entstanden über den in `06-04` reparierten Pfad
(`absenceService.initializeVacationBalance()`, der vor dem Fix nie pro rata rechnete):

| Nutzer | userId | `vacation_balance` 2025 | Journal 2025 (eine `entitlement`-Buchung) |
|---|---|---|---|
| Karin Jochem | 2 | `entitlement=7, carryover=0, taken=0, remaining=7` | `+7`, "Jahresanspruch 2025 (rückwirkend erzeugt)" |
| Christine Glas | 3 | `entitlement=13, carryover=0, taken=0, remaining=13` | `+13`, "Jahresanspruch 2025 (rückwirkend erzeugt)" |

Beide Werte, beide Journaleinträge und beide Beschäftigungs-Belege wurden für diesen Plan erneut
gegen die Entwicklungsdatenbank nachgeprüft (Stand 2026-08-21) — der Koordinator hatte
ausdrücklich darauf hingewiesen, dass sich die Zahlen seit seiner Analyse geändert haben
könnten; sie stimmen exakt mit den gemeldeten Werten überein.

**Warum eine Gegenbuchung genügt, keine Löschung nötig ist:** `syncTakenFromJournal()`
(`vacationTransactionService.ts:138`) berechnet `taken = entitlement + carryover −
Journalsaldo`. `remaining` ist eine generierte, virtuelle Spalte
(`server/src/database/schema.ts:213`: `GENERATED ALWAYS AS (entitlement + carryover - taken)
VIRTUAL`) — aufgelöst also immer gleich dem Journalsaldo. Eine `correction`-Buchung von −7 bzw.
−13 bringt den Journalsaldo auf 0; `taken` wird automatisch von `recordVacationTransaction()`
neu synchronisiert (jede Buchung ruft `syncTakenFromJournal()` synchron auf); `remaining` folgt
automatisch, da virtuell. Nichts muss gelöscht werden, und der bestehende
Neuanlage-Journaleintrag bleibt als Beleg stehen.

**Entscheidung: `entitlement` wird zusätzlich auf 0 korrigiert, nicht nur der Journalsaldo.**
Zwei Varianten wurden geprüft:
- Nur eine `correction`-Buchung von −7/−13, `entitlement` bleibt bei 7/13: `taken` würde sich
  nach `syncTakenFromJournal()` automatisch auf 7/13 setzen (`7 + 0 − 0 = 7`). Der
  Kontoauszug-Header aus Phase 8 (`desktop/src/components/vacation/VacationTransactions.tsx`,
  `Anspruch {entitlement} + Übertrag {carryover} − Genommen {taken}`) zeigt dann „Anspruch 7 +
  Übertrag 0 − Genommen 7" — rechnerisch 0 Resttage, aber irreführend: Karin hat nie 7 Tage
  Urlaub genommen.
- `entitlement` wird per Korrektur auf 0 gesetzt (gewählt): Header zeigt „Anspruch 0 + Übertrag 0
  − Genommen 0" — korrekt UND verständlich. Die Buchungszeilen zeigen in beiden Varianten den
  vollen Vorgang (ursprüngliche Anspruchsbuchung + Korrektur), das Argument für die Wahl ist
  ausschließlich die Kopfzeile.

Diese Korrektur nutzt dafür **keinen neuen Mechanismus**, sondern den bereits produktiven
Korrektur-Pfad `vacationBalanceService.updateVacationBalance(id, { entitlement: 0, reason,
actorId: null })`: er bucht die Feld-Differenz (`newValue − oldValue`, hier `0 − 7 = −7`) als
`correction`-Transaktion mit `buildCorrectionDescription()` (Format: `Korrektur Anspruch 7 → 0
(Grund: ...)`) und aktualisiert `vacation_balance.entitlement` atomar in derselben
`db.transaction()` — exakt derselbe Weg, den ein Admin über die Oberfläche auslösen würde. Kein
`taken` wird explizit übergeben, also greift die Selbstabgleich-Prüfung in
`updateVacationBalance()` nicht ein; `recordVacationTransaction()` synchronisiert `taken`
danach automatisch aus dem Journal.

**Idempotenz:** Analog zum Muster aus `vacationBackfillService.ts`
(`BACKFILL_MARKER`/`hasExistingBackfill()`) trägt der `reason`-Text einen eindeutigen,
lesbaren Marker (`[BACKFILL-06-07]`), der als Teil der von `buildCorrectionDescription()`
erzeugten Beschreibung im Journal landet. Vor jedem Lauf prüft das Skript, ob für
`(userId, year)` bereits eine `correction`-Buchung mit diesem Marker existiert — falls ja, wird
dieses Konto übersprungen, nicht erneut gebucht.
