# Phase 09.1: Code-Review-Bericht

**Tiefe:** standard

## Zusammenfassung

Der Kern der Phase ist handwerklich sauber: `overtimeRecalcRunner.ts` öffnet tatsächlich
keine eigene Verbindung, die Fehlerisolierung pro Nutzer ist umgesetzt und belegt, der
Produktionsschutz in `fixOvertime.ts` steht an der richtigen Stelle (nur importsichere
Module am Kopf, `assertNotProduction()` synchron vor jedem `await import()`), und
`npx tsc --noEmit` läuft über den gesamten `server/src`-Baum inklusive der fünf
verschobenen Skripte fehlerfrei durch.

Die Prüfung fördert dennoch vier Befunde zutage, die produktionswirksam sind:

1. Der neue crontab-Bereinigungsschritt kann den **gesamten** crontab löschen — genau den
   wöchentlichen DB-Sync-Eintrag, den sein eigener Kommentar zu schützen verspricht. Das
   ist eine **neu eingeführte** Regression: die alte Fassung hängte mit
   `; echo "$CRON_COMMAND"` immer mindestens eine Zeile an, die neue nicht mehr.
2. `fixOvertime.ts` ruft am Ende `db.close()` auf. Das ist exakt die Operation, die laut
   `.planning/debug/wal-abgehaengt-20260827.md` die WAL des Serverprozesses abhängt. Mit
   `--allow-production` reproduziert das Werkzeug den Vorfall, statt ihn zu vermeiden.
3. Die Produktionsdatenbank wird bei **jedem** Deployment weiterhin aus zwei fremden
   Prozessen geöffnet und wieder geschlossen (`migrate:prod`, `validate:schema`) — beide
   laufen, während PM2 den Server noch bedient. Die Aussage in `.claude/CLAUDE.md`, es
   gebe „keinen externen `npx tsx`-Prozess mehr", trifft nicht zu.
4. `sync-db.ts` kopiert in beiden Betriebsarten den unmigrierten Altbestand
   `server/database.db` (nachgemessen: 831 488 Bytes, Zeitstempel 2026-04-02) über die
   Arbeitsdatenbank und zerstört bei einem zweiten Lauf am selben Tag die eigene Sicherung.

Zwei weitere Punkte hängen unmittelbar am Phasenziel: `scripts/database/setup-cron.sh` liegt
unverändert im Repository und wird in `scripts/README.md` und `ENV.md` weiterhin als der Weg
beschrieben, den Nachtlauf zu aktivieren — es installiert genau den Cron-Eintrag, den der
neue Bereinigungsschritt entfernt (WR-16). Und WR-03 (`busy_timeout`) ist auf der falschen
Seite angebracht: die Serververbindung bekommt den Timeout, die Fremdprozesse aus CR-03, die
tatsächlich mit ihr konkurrieren, nicht.

### CR-01: crontab-Bereinigung kann den kompletten crontab löschen (neue Regression)

**Datei:** `.github/workflows/deploy-server.yml:133-137`, `.github/workflows/deploy-staging.yml:124-128`

**Problem:**
```bash
(crontab -l 2>/dev/null | grep -v "fix-overtime.ts") | crontab - || {
  echo "⚠️  Cron cleanup failed, continuing..."
}
```
`crontab -` ersetzt den **gesamten** crontab durch das, was auf stdin ankommt. Der Diff
gegen `cff801c` zeigt, dass die Vorgängerfassung
`(crontab -l 2>/dev/null | grep -v "fix-overtime.ts"; echo "$CRON_COMMAND") | crontab -`
lautete — das `echo` garantierte immer mindestens eine Zeile. Dieser Schutz ist entfallen.

Fehlerfälle, die jetzt einen leeren crontab installieren:
- `crontab -l` schlägt fehl (Rechteproblem, `/var/spool/cron` nicht lesbar, cron-Daemon
  gestört). stderr ist mit `2>/dev/null` unterdrückt, stdout ist leer → `crontab -` schreibt
  einen leeren crontab.
- `grep -v` filtert alle Zeilen weg.

Der `|| { echo ... }`-Zweig greift in **keinem** dieser Fälle, weil `crontab -` erfolgreich
terminiert — es hat ja etwas (nämlich nichts) installiert. Der Schritt läuft bei jedem
Deployment und der Kommentar direkt darüber betont ausdrücklich, dass ein weiterer,
wöchentlicher DB-Sync-Eintrag auf demselben Server erhalten bleiben muss. Genau der wäre weg,
still, ohne Fehlermeldung, im `success`-Deployment.

Verschärfend: der Schritt ist eine Einmal-Migration, läuft aber unbefristet bei jedem
Deployment mit.

**Fix:** Erst einlesen, Erfolg prüfen, nur bei einem echten Treffer schreiben und danach
gegenlesen:
```bash
echo "🧹 Removing legacy overtime cron entry (Phase 9.1, D-03)..."
if CRON_BEFORE=$(crontab -l 2>/dev/null); then
  if echo "$CRON_BEFORE" | grep -q "fix-overtime.ts"; then
    echo "$CRON_BEFORE" | grep -v "fix-overtime.ts" | crontab -
    # Gegenlesen: der Sync-Eintrag muss ueberlebt haben
    if echo "$CRON_BEFORE" | grep -q "sync" && ! crontab -l 2>/dev/null | grep -q "sync"; then
      echo "❌ FATAL: crontab-Bereinigung hat fremde Eintraege entfernt!"
      echo "$CRON_BEFORE" | crontab -   # wiederherstellen
      exit 1
    fi
    echo "✅ Legacy-Eintrag entfernt"
  else
    echo "✅ Kein Legacy-Eintrag vorhanden - nichts zu tun"
  fi
else
  echo "ℹ️  Kein crontab vorhanden - nichts zu tun"
fi
```

### CR-02: `fixOvertime.ts` schließt die Verbindung — genau die Operation, die die WAL abhängt

**Datei:** `server/src/scripts/fixOvertime.ts:163-167`

**Problem:**
```ts
  } finally {
    db.close();
  }

  process.exit(exitCode);
```
Der Kopfkommentar des Werkzeugs beschreibt den Mechanismus korrekt: SQLite räumt WAL und SHM
beim `sqlite3_close` auf, sobald der schließende Prozess kurz die exklusive Sperre bekommt.
Dann tut das Werkzeug in Zeile 164 genau das. Mit `--allow-production` gegen
`/home/ubuntu/databases/production.db` ist das eine wortgetreue Wiederholung des Vorfalls aus
`.planning/debug/wal-abgehaengt-20260827.md` — der einzige Unterschied zum abgelösten
`scripts/fix-overtime.ts` ist, dass hier ein Warnhinweis auf stdout steht.

Beim harten Prozessende (`process.exit`) läuft `sqlite3_close` **nicht**; SQLite räumt WAL/SHM
dann nicht auf und die Dateizeiger des Serverprozesses bleiben verknüpft. Das explizite
`db.close()` ist also strikt schlechter als gar kein Close.

Ebenso falsch wäre `shutdownDatabase()`: dessen `wal_checkpoint(TRUNCATE)` ist für den
*Eigentümer* der Verbindung richtig, für einen Zweitprozess auf derselben Datei aber genau
der Auslöser.

Das `finally` greift zusätzlich im Fehlerpfad, also gerade dann, wenn ohnehin schon etwas
schiefging.

**Fix:**
```ts
  // KEIN db.close(): sqlite3_close raeumt WAL und SHM auf, sobald der schliessende Prozess
  // kurz die exklusive Sperre bekommt - und haengt damit die WAL eines gleichzeitig
  // laufenden Serverprozesses ab (.planning/debug/wal-abgehaengt-20260827.md). Beim harten
  // process.exit() laeuft sqlite3_close nicht; die Dateizeiger des Servers bleiben intakt.
  // shutdownDatabase() waere hier ebenso falsch - dessen wal_checkpoint(TRUNCATE) ist genau
  // der Ausloeser.
  const bilanz = await runOvertimeRecalcForAllUsers({ ... });
  ...
  process.exit(exitCode);
```
Sollte ein Checkpoint gewünscht sein, gehört er über die API des laufenden Servers
(`createBackup()` in `backupService.ts`), nicht in diesen Prozess.

### CR-03: Produktionsdatenbank wird bei jedem Deployment weiterhin aus zwei Fremdprozessen geöffnet und geschlossen

**Dateien:** `.github/workflows/deploy-server.yml:104,113` → `server/src/scripts/migrate.ts:128,165`,
`server/src/scripts/validateSchema.ts:156,221`

**Problem:** Der Deploy-Ablauf ist:
- Zeile 50: `export DATABASE_PATH=/home/ubuntu/databases/production.db`
- Zeile 104: `npm run migrate:prod` → `migrate.ts:128` `new Database(dbPath)` (schreibend),
  `migrate.ts:165` `db.close()` im `finally`
- Zeile 113: `npm run validate:schema` → `validateSchema.ts:156` `new Database(dbPath, { readonly: true })`,
  `validateSchema.ts:221` `db.close()` im `finally`
- Zeile 162: **erst jetzt** `pm2 stop timetracking-server`

Beide Skripte laufen also als eigener `npx tsx`-Prozess auf `production.db`, **während der
Serverprozess sie offen hält**, und beide schließen ihre Verbindung selbst. Das ist derselbe
Mechanismus wie in CR-02 und exakt das, was `.claude/CLAUDE.md` unter „Produktionsdatenbank:
niemals aus einem eigenen Prozess öffnen" verbietet — ausdrücklich einschließlich
`readonly`.

Die Phase hat den nächtlichen Cron beseitigt (richtig), aber die beiden Deploy-Zugriffe
stehen unverändert. Die Aussage in `.claude/CLAUDE.md` — „es gibt keinen externen `npx
tsx`-Prozess mehr, der sich die exklusive Sperre holen und die WAL abhängen könnte" — ist
damit falsch; sie stimmt nur für den Nachtlauf, nicht für den Deploy-Weg. Bei ~1 Deployment
pro Tag ist die Trefferwahrscheinlichkeit zwar geringer als beim 03:00-Cron (Server ist
tagsüber nicht idle), aber nicht null — und die laufende Zwei-Nächte-Beobachtung (D-17) kann
diesen Pfad gar nicht sehen.

**Fix (Mindestmaßnahme, kein Umbau):** Reihenfolge im Workflow ändern, sodass beide Schritte
nach `pm2 stop`/`pm2 delete` und vor `pm2 start` liegen — dann gibt es nachweislich keinen
zweiten Halter:
```bash
            # Server anhalten, BEVOR ein Fremdprozess production.db anfasst
            pm2 stop timetracking-server || true
            pm2 delete timetracking-server || true

            # Erst jetzt Migrationen und Schemapruefung (eigener Prozess, kein zweiter Halter)
            DATABASE_PATH=$DATABASE_PATH NODE_ENV=production npm run migrate:prod || { ... }
            DATABASE_PATH=$DATABASE_PATH NODE_ENV=production npm run validate:schema || true

            # ... dann pm2 start
```
Zusätzlich in `migrate.ts` und `validateSchema.ts` einen Vermerk aufnehmen, dass beide nur bei
gestopptem Server gegen `production.db` laufen dürfen. Alternativ (aufwendiger, aber
sauberer): den `.sql`-Migrationslauf in `runMigrations(db)` des Serverprozesses ziehen, dann
entfällt der Fremdprozess ganz.

### CR-04: `sync-db.ts` überschreibt die Arbeitsdatenbank mit dem Altbestand und zerstört die eigene Sicherung

**Datei:** `server/src/scripts/sync-db.ts:25,33,47,54,99`

**Problem — falsche Quelle:**
- `syncLocal()` (Zeile 33) nimmt `databaseConfig.productionPath`. Das ist laut
  `src/config/database.ts:41` fest `server/database.db`.
- `syncRemote()` (Zeile 25) lädt `ORACLE_DB_PATH = '/home/ubuntu/TimeTracking-Clean/server/database.db'`.

`.claude/CLAUDE.md` stellt ausdrücklich fest: „`server/database.db` ist NICHT die
Arbeitsdatenbank. Unmigrierter Altbestand von April 2026 (ohne `user_work_periods`)". Lokal
nachgemessen: 831 488 Bytes, Zeitstempel 2026-04-02. Der Symlink auf `production.db` wurde am
20.08.2026 entfernt. `npm run db:sync` kopiert also einen Stand von vor v3.0 über
`server/database/development.db` — die Datenbank, gegen die die gesamte Testsuite läuft.

**Problem — Sicherung wird beim zweiten Lauf zerstört:**
```ts
const timestamp = new Date().toISOString().replace(/[:.]/g, '-').split('T')[0];
const backupPath = developmentPath.replace('.db', `.backup.${timestamp}.db`);
```
`split('T')[0]` verwirft den Zeitanteil komplett; der Dateiname enthält nur das Datum.
Ablauf: Lauf 1 sichert die gute `development.db` nach `development.backup.2026-08-29.db` und
überschreibt sie mit dem Altbestand. Lauf 2 am selben Tag sichert den **Altbestand** unter
denselben Namen — die gute Kopie ist weg. Kein Hinweis, kein Abbruch.

Nebenbei: `.replace(/[:.]/g, '-')` ist dadurch wirkungslos, und
`toISOString().split('T')[0]` ist in `.claude/CLAUDE.md` ausdrücklich verboten (UTC-Verschiebung).

**Fix:**
```ts
// Quelle: die tatsaechliche Produktionsdatenbank, nicht der Altbestand server/database.db
// (kein Symlink mehr seit 20.08.2026). Ohne DATABASE_PATH kein stiller Rueckfall.
const productionPath = process.env.SYNC_SOURCE_DB;
if (!productionPath) {
  console.error('❌ SYNC_SOURCE_DB nicht gesetzt (z. B. /home/ubuntu/databases/production.db).');
  process.exit(2);
}

// Sicherungsname mit Uhrzeit, damit ein zweiter Lauf am selben Tag nichts ueberschreibt.
const timestamp = formatDate(new Date(), 'yyyy-MM-dd_HH-mm-ss');
const backupPath = developmentPath.replace(/\.db$/, `.backup.${timestamp}.db`);
if (existsSync(backupPath)) {
  console.error(`❌ Sicherung existiert bereits: ${backupPath}`);
  process.exit(1);
}
```
Zusätzlich `ORACLE_DB_PATH` korrigieren bzw. den Fernabruf ganz auf den kanonischen Weg
`scripts/sync-dev-db.sh` verweisen und `db:sync:remote` entfernen (siehe WR-02).

### WR-01: `busy_timeout` schützt nur die Seite, die keinen Konkurrenten mehr hat

**Dateien:** `server/src/database/connection.ts:13-17,51`; `server/src/scripts/migrate.ts:128`,
`server/src/scripts/seed.ts:144`, `server/src/scripts/validateSchema.ts:156`,
`server/src/scripts/sync-db.ts:59,118`

**Problem:** Der Begründungskommentar in `connection.ts:13-16` nennt als Szenario
„der naechtliche Neuberechnungslauf und der Serverprozess, die getrennte Verbindungen auf
dieselbe production.db hielten". Genau dieses Szenario hat WR-05 in derselben Phase beseitigt.
Übrig bleiben als Zweitprozesse `migrate.ts`, `validateSchema.ts` und `seed.ts` — und keiner
davon setzt `busy_timeout`, weil keiner über `connection.ts` geht, sondern direkt
`new Database(dbPath)` aufruft. SQLite-Standard ist 0 ms, also sofortiger `SQLITE_BUSY`.

Konkrete Folge: kollidiert `migrate:prod` beim Deployment mit einem Schreibvorgang des noch
laufenden Servers (siehe CR-03), bricht die Migration sofort ab und das Deployment gilt als
fehlgeschlagen — obwohl 5 s Warten gereicht hätten. Der Nachweistest
`connection.busyTimeout.test.ts` belegt korrekt, dass die Serververbindung wartet, sagt über
die Skripte aber nichts aus.

**Fix:** Eine gemeinsame Hilfsfunktion für Skriptverbindungen, die dieselbe Konstante trägt:
```ts
// src/database/openScriptConnection.ts
export const BUSY_TIMEOUT_MS = 5000;
export function openScriptConnection(dbPath: string, options?: Database.Options) {
  const database = new Database(dbPath, options);
  database.pragma('busy_timeout = ' + BUSY_TIMEOUT_MS);
  const gelesen = database.pragma('busy_timeout', { simple: true }) as number;
  if (gelesen !== BUSY_TIMEOUT_MS) {
    throw new Error(`busy_timeout nicht gesetzt: erwartet ${BUSY_TIMEOUT_MS}, gelesen ${gelesen}`);
  }
  return database;
}
```
und `migrate.ts`, `seed.ts`, `validateSchema.ts`, `sync-db.ts` darauf umstellen.

### WR-04: Keine Wiedereintrittssperre für den Neuberechnungslauf

**Dateien:** `server/src/services/overtimeRecalcRunner.ts:51`,
`server/src/services/cronService.ts:171-183`, `server/src/server.ts:288`

**Problem:** Drei Aufrufer teilen sich `runOvertimeRecalcForAllUsers()`, aber nichts verhindert
Überlappung:

- `cronService.ts:171` registriert den 03:15-Lauf. node-cron wartet die `async`-Rückrufe

```ts
  laufAktiv = true;
  try {
    // ... bisheriger Rumpf
  } finally {
    laufAktiv = false;
  }
}
```

### WR-05: Signalbehandler werden erst nach dem gesamten Serverstart registriert

**Datei:** `server/src/server.ts:329-331` (Registrierung), `:212-258` (ungeschützter Bereich)

**Problem:** `process.on('SIGTERM', ...)` steht ganz am Ende von `startServer()`. Alles davor —
`seedDatabase()`, `runMigrations(db)`, `resetStaleChainGuardSuspension()`,
`initializeHolidays()` (Netzwerkabruf, kann Sekunden dauern) — läuft ohne Signalbehandler.
Trifft in diesem Fenster ein SIGTERM ein (PM2 beim Deployment, `pm2 restart` durch den
Bediener), stirbt der Prozess mit Node-Standardverhalten: kein `shutdownDatabase()`, kein
`wal_checkpoint(TRUNCATE)`. Der Kommentar bei `:295-303` beschreibt genau die Gefahrenlage, die
in diesem Fenster wieder besteht.

Dasselbe gilt für den Fehlerpfad `:332-335`: `process.exit(1)` ohne `shutdownDatabase()`.

**Fix:** Handler an den Anfang von `startServer()` ziehen und `httpServer` optional halten:
```ts
async function startServer() {
  let httpServer: import('http').Server | undefined;
  let shutdownInProgress = false;

  const shutdown = (signal: NodeJS.Signals) => {
    if (shutdownInProgress) return;
    shutdownInProgress = true;
    logger.info({ signal }, '🛑 Herunterfahren eingeleitet');
    httpServer?.close(() => logger.info('🔌 HTTP-Server geschlossen'));
    shutdownDatabase();
    setTimeout(() => process.exit(0), 500).unref();
  };
  process.on('SIGTERM', () => shutdown('SIGTERM'));
  process.on('SIGINT', () => shutdown('SIGINT'));

  try {
    ...
  } catch (error) {
    logger.error({ err: error }, '❌ Failed to start server');
    shutdownDatabase();   // auch im Fehlerpfad Pruefpunkt setzen
    process.exit(1);
  }
}
```

### WR-06: Der Serverstart-Lauf kann mitten im Nutzerkreis abgeschnitten werden

**Datei:** `server/src/server.ts:288-290`, `:304-327`

**Problem:** Der Serverstart-Lauf ist bewusst nicht blockierend (nachvollziehbar begründet,
Health-Check soll nicht warten). `shutdown()` ruft aber `shutdownDatabase()` sofort auf, ohne
zu prüfen, ob der Lauf noch aktiv ist. Bei einem `pm2 restart` kurz nach dem Start wird der
Lauf mitten in der Nutzerschleife abgeschnitten: die Proxy-Zugriffe werfen dann „Database is
shutting down", jeder Rest-Nutzer landet als `fehlgeschlagen` im Protokoll. Fachlich heilt der
nächste Lauf das, aber das Fehlerprotokoll füllt sich mit Rauschen, das von echten Defekten
nicht unterscheidbar ist (relevant für die laufende D-17-Beobachtung).

**Fix:** Laufzustand exportieren und beim Herunterfahren gezielt vermerken:
```ts
// overtimeRecalcRunner.ts
export function istRecalcAktiv(): boolean { return laufAktiv; }   // vgl. WR-04

// server.ts, in shutdown()
if (istRecalcAktiv()) {
  logger.warn('⚠️ Neuberechnungslauf war noch aktiv und wird abgebrochen - naechster Lauf holt nach');
}
shutdownDatabase();
```

### WR-07: Fehlerobjekt verschluckt; `finally { db.close() }` läuft im Fehlerfall nie

**Dateien:** `server/src/scripts/migrate.ts:160-166`, `server/src/scripts/seed.ts:183-189`

**Problem:**
```ts
} catch (error) {
  console.error('\n❌ Migration failed! Database may be in an inconsistent state.');
  console.error('   Please review the error and fix the migration file.\n');
  process.exit(1);
} finally {
  db.close();
}
```
Zwei Defekte in fünf Zeilen:
1. `error` wird nie ausgegeben. `applyMigration()` protokolliert zwar selbst, aber Fehler aus
   `initMigrationsTable()` und `getAppliedMigrations()` (z. B. `SQLITE_BUSY`, siehe WR-01,
   oder ein korruptes Schema) verschwinden spurlos. Im Deploy-Protokoll steht dann nur
   „Migration failed!" ohne jede Ursache — genau der Moment, in dem man sie braucht.
2. `process.exit(1)` beendet den Prozess sofort; `finally` läuft danach **nicht** mehr. Das
   Verhalten unterscheidet sich also zwischen Erfolgs- und Fehlerpfad, ohne dass das
   beabsichtigt oder dokumentiert wäre.

`seed.ts:183-186` ist wortgleich betroffen.

**Fix:**
```ts
} catch (error) {
  console.error('\n❌ Migration failed! Database may be in an inconsistent state.');
  console.error(error);
  db.close();
  process.exit(1);
} finally {
  // Erfolgsfall
  if (db.open) db.close();
}
```
(Für den Produktionspfad zusätzlich CR-03 beachten.)

### WR-10: Der Nebenläufigkeitsnachweis hängt an Wanduhr-Schwellen

**Datei:** `server/src/database/connection.busyTimeout.test.ts:114-118,188,219`

**Problem:** Der Sperrhalter hält die Sperre über einen festen `setTimeout(..., 1000)`, der
**ab dem `LOCKED`-Schreiben** läuft. Die Prüfungen sind:
- Fall (2): `expect(dauer).toBeGreaterThanOrEqual(300)`
- Fall (3): `expect(dauer).toBeLessThan(250)`

Beide sind gegenüber Last empfindlich, und zwar in unterschiedliche Richtungen:
- Fall (2) wird **rot**, wenn der Testprozess zwischen `LOCKED` und dem `INSERT` mehr als
  ~700 ms braucht (Windows-Prozessstart, Virenscanner, ausgelasteter CI-Läufer) — dann ist die
  Sperre bereits freigegeben und `dauer` fällt unter 300. Der Kommentar bezeichnet die
  Schwelle als „bewusst grosszuegig fuer langsame Laeufer"; tatsächlich benachteiligt sie
  langsame Läufer.
- Fall (3) wird **rot**, wenn der Sperrhalter vor dem `INSERT` der rohen Verbindung committet
  hat — dann wird gar kein `SQLITE_BUSY` geworfen und `geworfenerFehler` bleibt `undefined`.
- Fall (3) wird zusätzlich rot, wenn ein einzelner `INSERT` auf einem belasteten Windows-Läufer
  über 250 ms braucht.

Ein rot blinkender WR-03-Nachweis ist schlimmer als kein Nachweis, weil er künftig
weggeklickt wird.

**Fix:** Haltedauer erhöhen und die Sperre erst mit einem Signal freigeben statt per fester
Frist:
```js
// Sperrhalter: haelt, bis der Testprozess SIGTERM schickt (max. 10 s als Notbremse)
process.on('SIGTERM', () => { db.exec('COMMIT'); process.exit(0); });
setTimeout(() => { db.exec('COMMIT'); process.exit(0); }, 10000);
```
und im Test nach `warteAufLocked()` den `INSERT` in einem Nebenlauf starten, den Sperrhalter
nach ~500 ms per `kind.kill('SIGTERM')` freigeben und nur noch prüfen, dass der `INSERT`
*erfolgreich* war (Fall 2) bzw. `SQLITE_BUSY` warf (Fall 3) — ohne Millisekundenschwellen.

### WR-11: `needs: []` gated nichts — der Kommentar behauptet das Gegenteil

**Dateien:** `.github/workflows/deploy-server.yml:16`, `.github/workflows/deploy-staging.yml:28`

**Problem:**
```yaml
    needs: []  # Will be auto-skipped if test.yml fails
```
`needs: []` bedeutet „keine Abhängigkeiten". Der Job wird **nicht** übersprungen, wenn
`test.yml` fehlschlägt — beide Workflows hängen am selben `push`-Ereignis und laufen parallel.
Es gibt in `deploy-server.yml` weder einen Type-Check- noch einen Audit-Schritt (entgegen der
Beschreibung in `.claude/CLAUDE.md`: „Type-Check → Security-Audit → SSH → …"). Nicht
kompilierender oder testroter Code geht damit ungehindert auf die Produktion; der Kommentar
erzeugt genau die falsche Sicherheit, die eine solche Lücke gefährlich macht.

**Fix:** Entweder echte Gates setzen —
```yaml
    needs: [test]     # test.yml muss als reusable workflow / job im selben Workflow liegen
```
— oder mindestens einen blockierenden Vorschritt einziehen:
```yaml
      - name: Type-Check
        run: cd server && npm ci && npx tsc --noEmit
```
Der irreführende Kommentar muss in jedem Fall weg.

### WR-12: Produktionsdeployment installiert Abhängigkeiten unreproduzierbar und führt Fremdcode aus

**Datei:** `.github/workflows/deploy-server.yml:78,90-91` (identisch `deploy-staging.yml:71,83-84`)

**Problem:**
```bash
curl -L https://www.npmjs.com/install.sh | sh 2>/dev/null || true
...
rm -rf node_modules package-lock.json 2>/dev/null || true
npm install --legacy-peer-deps
```
1. Ein Skript von einer externen URL wird bei jedem Deployment ungeprüft als Shell ausgeführt
   (kein Hash, keine Version, Fehler unterdrückt). Wird die Quelle kompromittiert, läuft der
   Fremdcode mit den Rechten von `ubuntu` auf dem Produktionsserver — demselben Konto, dem
   `/home/ubuntu/databases/production.db` gehört.
2. `package-lock.json` wird gelöscht und `npm install` löst die `^`-Bereiche aus
   `server/package.json` frisch auf. Der Produktionsserver bekommt damit potenziell eine
   andere Abhängigkeitsversion als die, gegen die lokal getestet wurde — betroffen sind u. a.

**Fix:**

```bash
            # Kein Fremdskript von einer URL, keine Loeschung der Lockdatei:
            # reproduzierbare Installation exakt nach package-lock.json.
            npm ci --omit=dev
```
Falls `--legacy-peer-deps` fachlich nötig bleibt, `package-lock.json` einchecken und
`npm ci --legacy-peer-deps` verwenden.

### WR-14: `SESSION_SECRET` wird beim Auslesen abgeschnitten und bei fehlendem Eintrag jedes Mal neu erzeugt

**Datei:** `.github/workflows/deploy-server.yml:150-156` (identisch `deploy-staging.yml:141-147`)

**Problem:**
```bash
SESSION_SECRET=$(grep "^SESSION_SECRET=" .env | head -1 | cut -d= -f2 || echo "")
if [ -z "$SESSION_SECRET" ]; then
  SESSION_SECRET=$(openssl rand -hex 32)
fi
```
1. `cut -d= -f2` liefert nur das Feld bis zum **ersten** `=`. Ein Base64-Secret mit
   `=`-Auffüllung oder ein Secret, das ein `=` enthält, wird still gekürzt — der Server läuft
   dann mit einem kürzeren, schwächeren Secret als hinterlegt, ohne jede Warnung.
2. Existiert `.env`, aber ohne `SESSION_SECRET`-Zeile, wird bei **jedem** Deployment ein neues
   Secret erzeugt und **nicht** in `.env` zurückgeschrieben. Ergebnis: alle Sitzungen aller
   Nutzer werden bei jedem Deployment ungültig, und die Ursache ist aus den Logs nicht
   ersichtlich (die Ausgabe meldet nur die Länge).

**Fix:**
```bash
SESSION_SECRET=$(grep "^SESSION_SECRET=" .env | head -1 | cut -d= -f2- || echo "")
if [ -z "$SESSION_SECRET" ]; then
  echo "⚠️  SESSION_SECRET fehlt in .env - erzeuge und PERSISTIERE ein neues"
  SESSION_SECRET=$(openssl rand -hex 32)
  echo "SESSION_SECRET=$SESSION_SECRET" >> .env
fi
```
