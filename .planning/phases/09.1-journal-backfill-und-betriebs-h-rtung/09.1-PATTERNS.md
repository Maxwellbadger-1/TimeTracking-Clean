## Pattern Assignments

### `server/src/services/cronService.ts` (service, event-driven) — `startOvertimeRecalcScheduler()`

**Analog:** dieselbe Datei, `startYearEndRolloverScheduler()` (Zeilen 61-129) — exaktes
Geschwister-Muster: Modul-Variable für den Task, Wächter gegen Doppelstart, `cron.schedule`
mit explizitem `timezone`, try/catch um die eigentliche Arbeit, `stop…()` und
`get…Status()`-Paar.

**Modul-Variable + Wächter** (Zeilen 12, 75-79):
```typescript
let yearEndRolloverTask: cron.ScheduledTask | null = null;
...
export function startYearEndRolloverScheduler(): void {
  if (yearEndRolloverTask) {
    logger.warn('⚠️  Year-end rollover scheduler already running');
    return;
  }
```
→ für den Überstunden-Scheduler: eigene Modul-Variable `overtimeRecalcTask`, derselbe
Wächter-Text mit eigenem Log-Präfix.

**Cron mit expliziter Zeitzone** (Zeilen 83-113, D-02 verlangt 03:15 statt 03:00):
```typescript
yearEndRolloverTask = cron.schedule(
  '5 0 1 1 *',
  () => {
    logger.info('🎊 Automated year-end rollover started...');
    try {
      const currentYear = new Date().getFullYear();
      const result = performYearEndRollover(currentYear);
      if (result.success) {
        logger.info({ ... }, '✅ Automated year-end rollover completed successfully');
      } else {
        logger.error({ errors: result.errors }, '❌ Automated year-end rollover failed');
      }
    } catch (error) {
      logger.error({ err: error }, '❌ Automated year-end rollover crashed');
    }
  },
  {
    timezone: 'Europe/Berlin', // CRITICAL: German timezone!
  }
);
```
→ Cron-Ausdruck für D-02: `'15 3 * * *'` (statt `'0 3 * * *'`, das im selben Prozess bereits
die Feiertags-Aktualisierung in `server.ts:242` belegt). Innerhalb des Callbacks läuft die
Nutzerschleife aus D-05 (Fehlerisolierung je Nutzer, s. u.) statt eines einzelnen
Funktionsaufrufs — der äußere try/catch bleibt trotzdem als zweite Sicherung bestehen,
falls die Schleife selbst außerhalb der inneren try/catch-Blöcke etwas wirft (z. B. beim
Laden der Nutzerliste).

**stop/status-Paar** (Zeilen 120-144) — wörtlich als Vorlage für
`stopOvertimeRecalcScheduler()` / `getOvertimeRecalcSchedulerStatus()` übernehmen, nur
Bezeichner und Cron-String austauschen.

**Importe** (Zeile 1-4):
```typescript
import * as cron from 'node-cron';
import { createBackup } from './backupService.js';
import { performYearEndRollover } from './yearEndRolloverService.js';
import logger from '../utils/logger.js';
```
→ für den neuen Scheduler zusätzlich `import { ensureOvertimeBalanceEntries } from './overtimeService.js';` und `import { db } from '../database/connection.js';` (dieselbe geteilte
Verbindung, D-01 — keine eigene `new Database(...)`-Zeile).

### `server/src/database/connection.busyTimeout.test.ts` (neu, Test, event-driven/concurrency)

**Analog:** `server/src/database/connection.shutdown.test.ts` — dieselbe Wegwerf-Datenbank-Infrastruktur, nur mit einer anderen Behauptung. Wörtlich übernehmbar:

**Frische, isolierte Verbindung je Test** (Zeilen 30-41):
```typescript
async function frischeVerbindung() {
  const dir = fs.mkdtempSync(path.join(os.tmpdir(), 'tt-shutdown-'));
  aufraeumen.push(dir);
  const dbPath = path.join(dir, 'test.db');

  // Muss VOR dem Import gesetzt sein: config/database.ts wertet den Pfad beim Laden aus.
  vi.stubEnv('DATABASE_PATH', dbPath);
  vi.resetModules();

  const modul = await import('./connection.js');
  return { dbPath, ...modul };
}
```

**Aufräumen** (Zeilen 20-28):
```typescript
const aufraeumen: string[] = [];

afterEach(() => {
  vi.unstubAllEnvs();
  vi.resetModules();
  for (const dir of aufraeumen.splice(0)) {
    fs.rmSync(dir, { recursive: true, force: true });
  }
});
```

**Was NEU dazukommt (D-08, kein Analogon im Projekt):** Statt einer einzelnen Verbindung
braucht der Nebenläufigkeitstest ZWEI echte `better-sqlite3`-Verbindungen auf dieselbe
Wegwerf-Datei — eine über `frischeVerbindung()` (trägt den `busy_timeout`, da sie durch
`initializeConnection()` läuft), eine zweite direkt über `new Database(dbPath)` mit
ebenfalls gesetztem `busy_timeout`. Ablauf: Verbindung A öffnet `BEGIN IMMEDIATE` und hält
die Schreibsperre; Verbindung B versucht währenddessen zu schreiben und muss — statt
sofort mit `SQLITE_BUSY` zu scheitern — bis zum `COMMIT`/`ROLLBACK` von A warten und danach
erfolgreich schreiben. `better-sqlite3` ist synchron; der Test muss die zweite Schreiboperation
deshalb in einem eigenen Zeitfenster (z. B. `setTimeout` vor dem `COMMIT` von A, dann A committen
und erst danach synchron auf B zugreifen — oder über ein Kind-Prozess-/Worker-Thread-Paar,
falls ein echter Blockierungsnachweis mit Zeitmessung verlangt ist) konstruieren. Der
Kopfkommentar von `connection.shutdown.test.ts:16-17` liefert den Stil für die Begründung,
warum eine eigene Temp-Datenbank verwendet wird — das ist direkt übertragbar.

**Gegenprobe, die D-08 explizit verlangt (nicht erfüllt durch einen reinen Konfigurationstest):**
Ein Test OHNE `busy_timeout` (zweite Verbindung mit `pragma('busy_timeout = 0')`) muss zeigen,
dass genau dort sofort `SQLITE_BUSY` geworfen wird — der Kontrast beweist, dass das Pragma die
Ursache des Wartens ist, nicht Zufall.
