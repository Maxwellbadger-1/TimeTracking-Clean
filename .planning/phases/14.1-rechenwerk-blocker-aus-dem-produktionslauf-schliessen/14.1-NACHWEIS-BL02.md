## 4. Festschreibung des Importstils (verbindlich für Plan 14.1-03 / BL-05)

**Gewählt: ein statischer Top-Level-Import.**

```ts
import { updateMonthlyOvertime, updateAllOvertimeLevels } from './overtimeService.js';
```

Er steht genau einmal, im Importkopf von `absenceService.ts`. **In dieser Datei darf für den
Lösch- und Anlegepfad kein zweiter Importstil entstehen** — Plan 14.1-03 (BL-05) übernimmt
diesen hier.

**Begründung 1 — kein Signaturwechsel.** `deleteAbsenceRequest`, `revertBalancesAfterDeletion`
und `deleteSickLeaveTimeEntries` sind synchron. Der Weg über `await import(…)`, wie ihn
`approveAbsenceRequest` und `rejectAbsenceRequest` (beide bereits `async`) nutzen, verlangte,
alle drei auf `async` umzustellen und `routes/absences.ts` sowie die Aufrufstellen in drei
Testdateien (`absencePeriodAwareness.test.ts`, `absenceVacationBooking.test.ts`,
`vacationEntitlementBooking.test.ts`) nachzuziehen — ein Eingriff in die öffentliche Signatur
ohne fachlichen Gewinn.

**Begründung 2 — der Zyklus trägt, und er ist nicht neu.** `absenceService` und `userService`
bilden bereits heute einen statischen ESM-Zyklus, der in der Produktion läuft:

```
absenceService.ts:6   import { getUserById }        from './userService.js'
userService.ts:4      import { getVacationBalance } from './absenceService.js'
overtimeService.ts    import { getUserById }        from './userService.js'
```

Der neue Import schließt in genau diesen bestehenden Zyklus hinein
(`absenceService → overtimeService → userService → absenceService`) und führt keine neue
Zyklusklasse ein. Tragfähig ist er, weil beides zutrifft: Weder `absenceService.ts` noch
`overtimeService.ts` verbrauchen importierte Bindungen auf Top-Level, und
`updateMonthlyOvertime` / `updateAllOvertimeLevels` sind gehoistete
`export function`-Deklarationen, die ausschließlich innerhalb von Funktionskörpern gerufen
werden — also nach vollständiger Modulauswertung.

**Das ist eine Herleitung. Belegt wird sie mit einer Ladeprobe zur Laufzeit.** Die Reihenfolge
ist wesentlich: `absenceService` zuerst, weil genau das der Einstieg ist, an dem ein Zyklus
brechen würde.

```ts
await import('./src/services/absenceService.js');
const ot = await import('./src/services/overtimeService.js');
console.log('typeof updateMonthlyOvertime   =', typeof ot.updateMonthlyOvertime);
console.log('typeof updateAllOvertimeLevels =', typeof ot.updateAllOvertimeLevels);
```

Ausgabe (`DATABASE_PATH=./database/development.db npx tsx ladeprobe.mts`):

```
typeof updateMonthlyOvertime   = function
typeof updateAllOvertimeLevels = function
LADEPROBE OK
PROBE_EXIT=0
```

Beide Bindungen sind `function`, keine ist `undefined`. Die Ladeprobe war ein einmaliges
Messwerkzeug und wurde nach der Messung entfernt; ihre vier Zeilen stehen oben vollständig und
sind jederzeit wiederholbar. Zusätzlich läuft der Zyklus in jedem Testlauf durch den echten
Pfad — `absenceDeletionRecalc.test.ts` importiert `absenceService` und ruft
`deleteAbsenceRequest` auf, das seinerseits die statisch importierten Funktionen benutzt.

**Was ausdrücklich unangetastet blieb:** Die beiden bereits funktionierenden
`await import('./overtimeService.js')`-Stellen in `approveAbsenceRequest` und
`rejectAbsenceRequest` (`grep -c` liefert unverändert **2**). Sie stehen in `async`-Funktionen,
laufen fehlerfrei und sind nicht Gegenstand von BL-02.

## 7. Ein neu beobachteter Nebenbefund — festgehalten, **nicht** repariert

**Was gemessen wurde.** Nach dem vollständigen Löschvorgang aus Test 2 stehen im selben
Protokoll zwei Zahlen nebeneinander, die auseinanderlaufen:

```
{"userId":42781,"month":"2026-07","transactionsCreated":32,"finalBalance":-176,…}   ← während der Löschtransaktion
{"userId":42781,"oldBalance":-168,"newBalance":-176,…,"msg":"✅ Updated work time account balance"}
{"userId":42781,"month":"2026-07","transactionsCreated":31,"finalBalance":-184,…}   ← nach der Löschung, aus updateMonthlyOvertime
```

`work_time_accounts.currentBalance` endet bei **−176,00 h**, das Journal und
`overtime_balance` enden bei **−184,00 h**.

**Ursache, am Quelltext abgelesen.** In `deleteAbsenceRequest` ruft
`revertBalancesAfterDeletion()` → `deleteSickLeaveTimeEntries()` die Funktion
`updateAllOvertimeLevels()` **innerhalb** der Löschtransaktion auf — zu diesem Zeitpunkt sind
die Zeiteinträge zwar schon weg, die Zeile in `absence_requests` aber noch da
(`DELETE FROM absence_requests` folgt erst danach). Der anschließende Aufruf von
`updateMonthlyOvertime()` läuft nach dem `DELETE` und rechnet richtig, berührt
`work_time_accounts` aber nicht (siehe den Kommentar am Ende von
`overtimeService.ts`: „REMOVED: Old Work Time Account sync"). Der Kontostand bleibt damit auf
dem Zwischenstand stehen.

**Warum das trotzdem BL-02 bestätigt und nicht widerlegt:** Vor dem Fix bewegte sich
`work_time_accounts` **gar nicht** (−168,00 h, unverändert). Nach dem Fix zieht der Wert nach.
Die verbleibende Restdifferenz von 8,00 h hat eine **andere** Ursache — die Reihenfolge von
Neuberechnung und Löschung innerhalb der Transaktion.

**Nicht mitrepariert.** D-07 (kein Sammelcommit, keine Vermischung zweier Befunde) und D-09
(neue Funde werden vermerkt, nicht nebenbei repariert) verbieten die Mitnahme. Der Eingriff
wäre auch kein Einzeiler: Er berührt die Reihenfolge innerhalb einer Transaktion, die
ausdrücklich als Atomaritätsklammer angelegt ist. Festgehalten in
`.planning/phases/14-absicherung-und-auslieferung/deferred-items.md`, Abschnitt „Aus Plan
14.1-02", und als Punkt **14.1-U5** in `14-UAT-SAMMLUNG.md`.
