### Die Kernfrage: Importzyklus bei einem statischen Top-Level-Import?

**Antwort: Nein, kein Zyklus.** `overtimeService.ts` importiert `absenceService.ts` an
keiner Stelle — weder statisch noch dynamisch. Vollständiger Import-Kopf von
`overtimeService.ts` (`:1-30`):
```typescript
import { db } from '../database/connection.js';
import { getDailyTargetHours, MissingWorkPeriodError } from '../utils/workingDays.js';
import logger from '../utils/logger.js';
import { /* ... */ } from '...';
import { getUserById } from './userService.js';
import { rebuildOvertimeTransactionsForMonth } from './overtimeTransactionRebuildService.js';
import { /* ... */ } from '...';
import { updateWorkTimeAccountBalance } from './workTimeAccountService.js';
import { unifiedOvertimeService } from './unifiedOvertimeService.js';
import { createWorkPeriodContext } from './workPeriodContext.js';
```
Die einzigen zwei Treffer für `absenceService` in `overtimeService.ts` sind reine
**Kommentare** (`:96`, `:171`), keine Imports. Ein statischer Top-Level-Import
`import { updateMonthlyOvertime, updateAllOvertimeLevels } from './overtimeService.js';` am
Kopf von `absenceService.ts` wäre damit **zyklusfrei** und die einfachste Lösung — beide
betroffenen Funktionen (`deleteAbsenceRequest`, `deleteSickLeaveTimeEntries`) sind aktuell
**nicht async**; ein statischer Import macht die Konvertierung zu `async` (und damit die
Anpassung aller Aufrufer, siehe unten) überflüssig. Sowohl `updateMonthlyOvertime`
(`overtimeService.ts:93`) als auch `updateAllOvertimeLevels` (`overtimeService.ts:191`) sind
bereits `export function` — kein Exportanpassung nötig.

**Alternative (falls Claude's Discretion `await import()` bevorzugt, konsistent mit den
bereits async Funktionen):** `deleteAbsenceRequest(id, deletedBy)` müsste zu
`async function` werden — Rückgabetyp bleibt `void`/`Promise<void>`. Aufrufer-Suche:
`export function deleteAbsenceRequest` wird u. a. aus `routes/absences.ts` aufgerufen (dort
ohnehin in einem async Route-Handler, trivial mit `await` zu ergänzen). `deleteSickLeaveTimeEntries`
ist eine lokale, nicht exportierte Funktion — ihre einzige Aufrufstelle
(`revertBalancesAfterDeletion()`, Zeile 1371) ist selbst nicht async und wird sowohl aus
`deleteAbsenceRequest` (Zeile 1187) als auch aus `rejectAbsenceRequest` (Zeile 1078, dort
bereits async) gerufen — eine Async-Kette bis in `deleteAbsenceRequest` hinein wäre nötig.

### Weg A — Definition: `absenceService.ts:1597-1632`, Funktion `deductOvertimeHours`

```typescript
function deductOvertimeHours(userId: number, hours: number): void {
  // Get all overtime balances for user, ordered by month
  const query = `
    SELECT * FROM overtime_balance
    WHERE userId = ? AND overtime > 0
    ORDER BY month ASC
  `;

  const balances = db.prepare(query).all(userId) as Array<{
    id: number;
    month: string;
    overtime: number;
  }>;

  let remainingHours = hours;

  // Deduct from oldest months first (FIFO)
  for (const balance of balances) {
    if (remainingHours <= 0) break;

    const toDeduct = Math.min(remainingHours, balance.overtime);

    // We need to reduce actualHours in the overtime_balance table
    // Since overtime is a VIRTUAL column (actualHours - targetHours),
    // we need to update actualHours
    const updateQuery = `
      UPDATE overtime_balance
      SET actualHours = actualHours - ?
      WHERE id = ?
    `;

    db.prepare(updateQuery).run(toDeduct, balance.id);

    remainingHours -= toDeduct;
  }
}
```

### Wichtiger struktureller Unterschied zu BL-02/Weg C: `createAbsenceRequest` ist NICHT async

`approveAbsenceRequest` (Zeile 796) und `rejectAbsenceRequest` (Zeile 984) sind beide
`export async function` und nutzen bereits `await import(...)`. `createAbsenceRequest`
(Zeile 403) ist dagegen **synchron** (`export function createAbsenceRequest(...)`, kein
`Promise`-Rückgabetyp). Für den fehlenden Neuberechnungsblock gibt es zwei Optionen:

1. **Statischer Import** (wie unter BL-02 empfohlen, zyklusfrei belegt): Kein
   Signaturwechsel nötig, `updateMonthlyOvertime` einfach synchron aufrufbar.
2. **`createAbsenceRequest` zu `async function` machen** und `await import(...)` nutzen,
   konsistent mit den beiden anderen Funktionen. **Blast-Radius**, falls diese Option gewählt
   wird: `createAbsenceRequest(...)` wird aufgerufen aus `routes/absences.ts:283` (dort
   bereits in einem async Route-Handler — trivial) **und** aus drei Testdateien mit
   zahlreichen Aufrufstellen: `absencePeriodAwareness.test.ts` (3×), `absenceVacationBooking.test.ts`
   (11×), `vacationEntitlementBooking.test.ts` (1×). Alle geprüften `it(...)`-Blöcke in diesen
   Dateien sind bereits `async` (sie rufen ohnehin `await approveAbsenceRequest(...)` auf),
   ein `await` vor `createAbsenceRequest(...)` wäre also mechanisch, aber an vielen Stellen
   nötig (mindestens 15 Aufrufstellen insgesamt).

**Empfehlung aus dem Befund:** Option 1 (statischer Import) hat den kleineren Blast-Radius
und ist konsistent mit der BL-02-Empfehlung — beide Blocker sollten denselben Lösungsweg
nutzen, nicht zwei verschiedene Importstile in derselben Datei einführen.

function isoDate(d: Date): string {
  const y = d.getFullYear();
  const m = String(d.getMonth() + 1).padStart(2, '0');
  const day = String(d.getDate()).padStart(2, '0');
  return `${y}-${m}-${day}`;
}

function firstOfMonthOffset(baseIsoDate: string, deltaMonths: number): string {
  const [y, m] = baseIsoDate.split('-').map(Number);
  const total = y * 12 + (m - 1) + deltaMonths;
  const newY = Math.floor(total / 12);
  const newM = (total % 12) + 1;
  return `${newY}-${String(newM).padStart(2, '0')}-01`;
}

function lastOfMonth(isoFirstOfMonth: string): string {
  const [y, m] = isoFirstOfMonth.split('-').map(Number);
  return isoDate(new Date(y, m, 0));
}
