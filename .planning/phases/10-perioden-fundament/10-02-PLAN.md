  <behavior>
    Jede Zeile ist ein eigener Test. „abgewiesen" heißt: `expect(() => …).toThrow(/…/)` mit
    einer Zusicherung auf den Text der Trigger- bzw. CHECK-Meldung, nicht nur „wirft
    irgendetwas".

    Erlaubt:
    - Erste Periode eines Nutzers, offen (`validTo = NULL`), ab seinem `hireDate`.
    - Anschlussperiode, deren `validFrom` exakt dem `validTo` der Vorgängerin entspricht.
    - Stichtagswechsel in zwei Schritten: UPDATE setzt `validTo` der offenen Periode,
      danach INSERT einer neuen offenen Periode ab genau diesem Datum.
    - UPDATE, das nur `weeklyHours` und `workSchedule` ändert, ohne Datumsverschiebung.
    - DELETE der letzten (offenen) Periode.
    - `DELETE FROM users WHERE id = ?` bei einem Nutzer mit drei verketteten Perioden räumt
      per Kaskade alles ab, ohne dass der DELETE-Trigger die Kaskade abbricht.

    Abgewiesen (Meldung enthält jeweils den zitierten Bestandteil):
    - Periode, die eine bestehende überlappt → „Überlappung".
    - Zweite offene Periode desselben Nutzers → Abbruch (Überlappungs-Trigger oder der
      partielle UNIQUE-Index; der Test hält fest, welcher der beiden greift).
    - Periode, die eine Lücke zur bestehenden Kette lässt → „Lücke".
    - UPDATE, das eine Lücke erzeugt (`validFrom` einer Anschlussperiode nach hinten
      verschoben) → „Lücke".
    - DELETE einer mittleren Periode bei noch existierendem Nutzer → „Lücke".
    - `validTo` gleich oder kleiner `validFrom` → CHECK-Verstoß.
    - `validFrom` in einem anderen Format (`2026-1-1`, `01.01.2026`, `2026-01-01T00:00:00Z`)
      → CHECK-Verstoß. Dieser Test ist der Riegel gegen die Zeitzonenfalle aus Phase 9.
    - Zwei Perioden desselben Nutzers mit identischem `validFrom` → UNIQUE-Verstoß.
    - Zwei **verschiedene** Nutzer dürfen sich überlappende Perioden haben (Gegenprobe: die
      Trigger filtern korrekt auf `userId`).
  </behavior>
  <action>
