# Phase 14.2 Plan 06: Befund F-6 (DATEV-Fehler als JSON statt Klartext) Summary

**`desktop/src/api/exports.ts` packt jetzt in beiden Exportfunktionen das Feld `error` aus dem Antwortkoerper aus, statt `response.text()` roh in die Fehlermeldung zu werfen — gemessen an fünf Antwortformen (echter 409, kaputter Koerper, interner Text mit Stacktrace/SQL/Pfad, je zweimal DATEV und CSV) erscheint durchgängig ein lesbarer deutscher Satz, nie JSON, nie ein internes Detail.**

## Accomplishments

### Task 1 — Fehlerkörper auspacken statt durchreichen (Commit `73a5742`)

`desktop/src/api/exports.ts` bekam eine private Hilfsfunktion `extractErrorMessage(response, fallback)` (Vorbild: `client.ts:99-113`) plus eine Sicherheitsschranke `containsInternalDetails()`:

1. `response.clone().text()` hält den Rohtext vor (Fallback auf einmaliges `response.text()`, falls `clone()` einmal nicht verfügbar sein sollte — geprüft: bei `universalFetch` ist es verfügbar, weil `tauriHttpClient.ts:129-133` eine echte neue `Response`-Instanz zurückgibt).
2. `JSON.parse` + Typwache `isErrorBody()` prüft auf ein nicht-leeres `error`-Feld — **kein** `code`-Feld, das existiert laut D-08-Korrektur nicht.
3. Trägt der Wert interne Details (`SQLITE_`, `at `-Zeilenanfang, SQL-Keywords, `/home/`, `C:\`), wird **nicht** er angezeigt, sondern ein deutscher Ersatzsatz mit HTTP-Statuscode; der Originalwert geht nur in `console.error` (gekürzt auf 200 Zeichen).
4. Kein JSON/kein `error`-Feld → derselbe Ersatzsatz.
5. Länge auf 500 Zeichen begrenzt.

Beide Aufrufstellen (`exportDATEV`, `exportHistoricalCSV`) werfen jetzt `new Error(await extractErrorMessage(response, '<Fallback>'))` — **ohne** vorangestelltes `DATEV Export fehlgeschlagen: `/`CSV Export fehlgeschlagen: `, weil der Server bereits einen vollständigen deutschen Satz liefert.
