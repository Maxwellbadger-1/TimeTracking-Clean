## F-1 — `POST /api/users/:id/reactivate` scheitert für bloß deaktivierte Nutzer

**Fundstelle (verifiziert):** `server/src/services/userService.ts:784-819`, Funktion
`reactivateUser`

```typescript
export function reactivateUser(id: number): UserPublic {
  try {
    // Check if user exists and is deleted
    const user = db.prepare('SELECT * FROM users WHERE id = ? AND deletedAt IS NOT NULL').get(id) as User | undefined;

    if (!user) {
      throw new Error('User not found or not deleted');
    }

    // Reactivate user
    const stmt = db.prepare(`
      UPDATE users
      SET deletedAt = NULL, status = 'active'
      WHERE id = ?
    `);
    ...
```

Zeile 787 verlangt zwingend `deletedAt IS NOT NULL`. Ein bloß deaktivierter Nutzer (per
`updateUser({isActive:false})`, siehe unten) hat `status='inactive'`, aber `deletedAt IS NULL`
— die Bedingung schlägt fehl, `reactivateUser` wirft `Error('User not found or not deleted')`.

**Route (verifiziert):** `server/src/routes/users.ts:524-569`

```typescript

  '/:id/reactivate',
  requireAuth,
  requireAdmin,
  (req: Request, res: Response<ApiResponse<UserPublic>>) => {
    try {
      const id = parseInt(req.params.id);
      ...
      const user = reactivateUser(id);
      ...
    } catch (error) {
      if (error instanceof Error && error.message.includes('not found')) {
        res.status(404).json({
          success: false,
          error: 'User not found or not deleted',

      }
      res.status(500).json({ success: false, error: 'Failed to reactivate user' });
    }
  }

```

Der englische Rohtext „User not found or not deleted" (NB-5) entsteht genau hier — bestätigt
D-04s Zuordnung zu F-1, nicht F-6.

**Deaktivierungsweg (Vorbild, bereits korrekt getrennt implementiert):**
`server/src/services/userService.ts:556-560`, in `updateUser`:

```typescript

  updates.push('status = ?');
  values.push(data.isActive ? 'active' : 'inactive');

```
schreibt `WHERE id = ? AND deletedAt IS NULL` (Zeile 575) — rührt `deletedAt` nie an.

**Soft-Delete-Weg (Vorbild):** `server/src/services/userService.ts:759-778`, `deleteUser`:
```typescript

  const stmt = db.prepare(`
    UPDATE users
    SET deletedAt = datetime('now'), status = 'inactive'
    WHERE id = ? AND deletedAt IS NULL
  `);
  ...

```

**Es gibt bereits einen zweiten, sauber benannten Weg:** `PATCH /api/users/:id/status`
(`server/src/routes/users.ts:575-630`, Service `updateUserStatus`, Zeile 824) setzt
`status='active'` OHNE `deletedAt`-Bedingung — genau der richtige Weg für einen bloß
deaktivierten Nutzer. **Der Desktop verwendet diesen Endpunkt aber nirgends** (projektweite
Suche in `desktop/src/hooks/` und `desktop/src/api/` ohne Treffer auf `/status` oder
`patch(`/users`). Nur `useReactivateUser()` (`desktop/src/hooks/useUsers.ts:292-297`) existiert
und ruft immer `POST /users/:id/reactivate`:

```typescript

  ...
  mutationFn: async (id: number) => {
    const response = await apiClient.post<User>(`/users/${id}/reactivate`);
    ...
```

**Für den Planer relevant:** D-04 lässt zwei Lösungswege offen — (a) `reactivateUser()`
erweitern, damit sie beide Zustände abdeckt (`deletedAt IS NOT NULL OR (status='inactive' AND
deletedAt IS NULL)`), oder (b) den Desktop auf den bereits bestehenden, ungenutzten
`PATCH /:id/status`-Endpunkt umstellen für den Fall „nur deaktiviert". Da F-4 (siehe unten) die
UI ohnehin zwingt, zwischen beiden Zuständen zu unterscheiden (`user.deletedAt` ist im
`User`-Typ bereits vorhanden, `desktop/src/types/index.ts:34`), liegt es nahe, dass die UI pro
Zustand den jeweils passenden Endpunkt aufruft — das ist eine Entscheidung für den Planer, kein
Fund.

**Lebender Testfall in `development.db` (verifiziert, read-only geprüft):**
```
users: sicht.p1228 — status prüfen mit deletedAt IS NULL, status='inactive'
```
(Nicht im Rahmen dieser Musterkarte verändert — nur zur Bestätigung, dass der Fall real
existiert, per `better-sqlite3` `{readonly:true}` gelesen.)

## Prüfsummen-Muster (D-01, aus Phase 14.1 D-08 — wiederverwenden, nicht neu erfinden)

**Fundstelle (exportiert, wiederverwendbar):** `server/src/scripts/purgeFutureOvertimeRows.ts:145-151,232-238`
```typescript
/** Die fuenf nach D-08 geschuetzten Tabellen — in ihnen wird keine Zeile angefasst. */
export const PROTECTED_TABLES: readonly string[] = [
  'time_entries',
  'absence_requests',
  'overtime_corrections',
  'vacation_balance',
  'vacation_transactions',
];

interface ProtectedMetric {
  table: string;
  rowCount: number;
  checksum: string;
}

/**
 * Zeilenzahl und SHA-256 ueber alle Zeilen einer Tabelle (nach `id` sortiert, JSON-
 * Darstellung) — dasselbe Verfahren wie in den Nachweisen zu BL-01 bis BL-04, damit die
 * Werte ueber die ganze Phase hinweg vergleichbar bleiben (D-08).
 */
function measureProtectedTables(db: BetterSqlite3Database): ProtectedMetric[] {
  return PROTECTED_TABLES.map((table) => {
    const rows = db.prepare(`SELECT * FROM ${table} ORDER BY id ASC`).all() as unknown[];
    const checksum = createHash('sha256').update(JSON.stringify(rows)).digest('hex');
    return { table, rowCount: rows.length, checksum };
  });
}

function printProtectedTables(label: string, metrics: ProtectedMetric[]): void {
  console.log(`=== D-08 — die fuenf geschuetzten Tabellen (${label}) ===`);
  for (const m of metrics) {
    console.log(`  ${m.table.padEnd(22)} Zeilen=${String(m.rowCount).padStart(5)}  sha256=${m.checksum}`);
  }
}
```
**Nur `PROTECTED_TABLES` ist exportiert** — `measureProtectedTables`/`printProtectedTables`
sind lokale Funktionen im Skript (nicht importierbar). Ein neues Nachweisskript in 14.2 muss
entweder `PROTECTED_TABLES` importieren und die beiden zehnzeiligen Funktionen erneut
schreiben, oder — sauberer — beide Funktionen zusätzlich exportieren (additive, risikofreie
Änderung an `purgeFutureOvertimeRows.ts`). Referenzwerte aus dem letzten Lauf (14.1-01,

## Vitest-Muster für einen Regressionstest an einem Endpunkt

**Wichtiger Befund:** Es gibt **kein** `supertest` im Projekt (grep über `server/src` ohne
Treffer). Server-Tests sind überwiegend **Service-Ebene** (direkter Funktionsaufruf, siehe
`14.1-PATTERNS.md`, Abschnitt „Testaufbau"). Für einen echten **Route**-Test (HTTP-Ebene, z. B.
um F-1s 404-Körper oder F-6s 409-Körper wörtlich zu prüfen) existiert bereits ein
funktionierendes Muster:

**Vorbild:** `server/src/routes/workPeriods.authorization.test.ts:1-76` (vollständiger Kopf)

import { db } from '../database/connection.js';
import type { SessionUser } from '../types/index.js';
import workPeriodsRouter from './workPeriods.js';
...

let server: Server | undefined;

function startTestServer(sessionUser: SessionUser | null): Promise<string> {
  const app = express();
  app.use(express.json());

  app.use((req: Request, _res: ExpressResponse, next: NextFunction) => {
    req.session = (sessionUser ? { user: sessionUser } : {}) as unknown as Request['session'];
