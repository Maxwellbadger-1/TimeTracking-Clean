## Der `git push` löst die Migrationen aus — nicht ein separater Schritt

1. `.github/workflows/deploy-server.yml:104` fährt `npm run migrate:prod` →
   `server/scripts/migrate.ts`. Dessen `getMigrationFiles()` filtert auf `.sql` und liest aus
   `server/database/migrations`. Die TypeScript-Migrationen **008 bis 015 laufen dort nicht.**
2. `server/src/server.ts:215` ruft beim Serverstart `await runMigrations(db)` →
   `server/src/database/migrationRunner.ts`, das `server/src/database/migrations/*.ts`
   alphabetisch lädt. **Hier** laufen 008–015 — im PM2-Start des Deployments, unbeaufsichtigt.
3. Scheitert eine dieser Migrationen, startet der Server nicht, der Health-Check des
   Workflows schlägt fehl, und die Produktionsdatenbank steht in einem Teilzustand. Genau
   dagegen wurde in Plan 14-04 die vollständige Folge auf einer Kopie erzwungen.

`origin/main` steht auf `0f2a03e` (gemessen per `git ls-remote origin main`, 23.08.2026);
lokal liegen 337 Commits und 293 geänderte Dateien davor.

<befund_fix_overtime_reihenfolge priority="hoch">
## `fix-overtime.ts` läuft im Workflow vor den Migrationen, die es braucht

`.github/workflows/deploy-server.yml:118` fährt
`DATABASE_PATH=$DATABASE_PATH NODE_ENV=production npx tsx scripts/fix-overtime.ts` — an einer
Stelle **vor** dem PM2-Start, also bevor `runMigrations()` gelaufen ist.

`server/scripts/fix-overtime.ts` importiert seit Plan 09-05 `ensureOvertimeBalanceEntries`
aus `../dist/services/overtimeService.js`. Diese Funktion delegiert an
`unifiedOvertimeService.calculateMonthlyOvertime()`, das je Tag `getDailyTargetHours()` ruft —
und das löst seit Phase 11 über `user_work_periods` auf. Diese Tabelle existiert auf der
Produktion vor Migration 008 nicht.

Zusätzlich hat `fix-overtime.ts` laut Befund WR-05 der Phase 9 **keine Fehlerisolierung je
Nutzer**: ein Fehler beim ersten Nutzer bricht den ganzen Lauf ab. Der Workflow fängt das mit
`|| { echo "⚠️ Overtime fix had issues, but continuing deployment..."; }` ab und läuft weiter.

Erwartete Wirkung ohne Gegenmaßnahme: Der Schritt scheitert vollständig, schreibt nichts und
das Deployment läuft weiter. Das ist *wahrscheinlich* harmlos — aber es ist ein Skript, das
`overtime_balance` per UPSERT schreibt und dabei gegen eine halbmigrierte Produktionsdatenbank
läuft. Diese Wette wird nicht eingegangen: Task 2 verschiebt den Schritt hinter den PM2-Start.
</befund_fix_overtime_reihenfolge>
