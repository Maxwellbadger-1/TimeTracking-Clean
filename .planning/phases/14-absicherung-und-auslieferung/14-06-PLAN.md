<befunde_zum_rueckweg>
Am Code und an der Umgebung geprüft:

1. **Der Deploy-Workflow legt bereits eine Sicherung an** —
   `.github/workflows/deploy-server.yml`, Zeile 62-64:
   `cp /home/ubuntu/databases/production.db /home/ubuntu/databases/backups/production.predeploy_$(date +%Y%m%d_%H%M%S).db || true`.
   Diese Sicherung ist als alleiniger Rückweg **nicht ausreichend**: sie nutzt `cp` statt
   `VACUUM INTO` (bei aktiver WAL-Datei gehen die jüngsten Transaktionen verloren, Lehre aus
   `06-07-SUMMARY.md`) und sie ist durch `|| true` **nicht fehlerabbrechend** — scheitert das
   Kopieren, läuft das Deployment trotzdem weiter. Die eigene Sicherung vor dem Push ist
   deshalb Pflicht und ersetzt sie nicht, sondern kommt zusätzlich.

2. **Der Rückweg ist zweiteilig.** Nach dem Deployment ist nicht nur die Datenbank verändert
   (Migrationen 008–015 laufen beim PM2-Start, `server/src/server.ts:215`), sondern auch der
   Code. Ein reines Zurückspielen der Datenbank bei laufendem neuem Code wäre wirkungslos:
   der nächste PM2-Neustart würde die Migrationen erneut anwenden. Der Rückweg muss daher
   **Code und Daten gemeinsam** zurücknehmen.

3. **Der Code-Rückweg ist ein Zurücksetzen auf `0f2a03e`** — den Stand, auf dem `origin/main`
   vor Plan 14-08 steht (gemessen per `git ls-remote origin main` am 23.08.2026). Dieser
   Commit-Hash gehört ins Runbook, damit er im Ernstfall nicht gesucht werden muss.

4. **Frische Daten sind per Dateizugriff nicht sichtbar** (WAL). Jede Verifikation nach einem
   Rückspielen läuft über die API oder `pm2 logs timetracking-server`, nicht über ein
   direktes Lesen der Datei (`14-CONTEXT.md`, „Existing Code Insights").

5. **`sqlite3`-CLI steht auf dem Arbeitsrechner nicht zur Verfügung** (Lehre aus Plan 03-01).
   Alle lokalen Datenbankoperationen laufen über `node -e` mit `better-sqlite3`. Auf dem
   Produktionsserver ist `better-sqlite3` unter
   `/home/ubuntu/TimeTracking-Clean/node_modules/better-sqlite3` vorhanden — `sync-dev-db.sh`
   nutzt genau diesen Pfad für sein serverseitiges `VACUUM INTO`.

**Abschnitt 1 — Sicherung vor dem Push (Pflichtschritt von Plan 14-08).**
Der Befehl, der über SSH auf dem Produktionsserver ein `VACUUM INTO` in
`/home/ubuntu/databases/backups/production.PRE-14-08_<YYYYMMDD>_<HHMMSS>.db` fährt, über
`node` mit dem absoluten Modulpfad
`/home/ubuntu/TimeTracking-Clean/node_modules/better-sqlite3` (dasselbe Muster wie
`sync-dev-db.sh`). Danach: Dateigröße prüfen, `integrity_check` gegen die Sicherung fahren,
und die Sicherung per `scp` auf den Arbeitsrechner holen. Eine Sicherung, die nur auf
demselben Server liegt, überlebt einen Ausfall dieses Servers nicht.

**Abschnitt 2 — Abbruchkriterien.** Wann wird zurückgerollt statt nachgebessert:
- Der Health-Check antwortet nach dem Deployment nicht mit `status: ok`
- `pm2 logs timetracking-server` zeigt einen Fehler aus `runMigrations`
- `PRAGMA integrity_check` auf der Produktion liefert etwas anderes als `ok`
- Der Vorher/Nachher-Vergleich zeigt einen Nutzer mit Differenz ungleich null, der nicht der
  Umstellungsfall ist
Jedes Kriterium mit dem Befehl, der es feststellt.

**Abschnitt 3 — Rückweg A: nur Daten.** Anwendbar, solange der Code noch nicht ausgeliefert
ist oder unverändert bleibt. Reihenfolge: `pm2 stop timetracking-server` → Sicherung per
`VACUUM INTO` in eine **neue** Datei zurückschreiben → alte `production.db` samt `-wal` und
`-shm` beiseiteschieben (umbenennen, nicht löschen) → neue Datei an die Stelle setzen →
`pm2 start` mit vollständiger Umgebungszeile aus `deploy-server.yml:161`
(`TZ=Europe/Berlin NODE_ENV=production DATABASE_PATH=/home/ubuntu/databases/production.db SESSION_SECRET=… ALLOWED_ORIGINS=…`)
→ Health-Check → Funktionstest.
Ausdrücklich vermerken: **Nur `pm2 start` mit gesetztem `DATABASE_PATH`.** Ohne die Variable
legt der Server eine leere Datenbank an; ohne `TZ=Europe/Berlin` rechnet er in UTC.

**Abschnitt 4 — Rückweg B: Daten und Code.** Anwendbar, sobald `runMigrations()` gelaufen ist.
Begründung voranstellen: Ein reines Zurückspielen der Daten ist wirkungslos, weil der nächste
PM2-Neustart die Migrationen 008–015 erneut anwendet. Reihenfolge:
`git push origin +0f2a03e:main` (Zurücksetzen des veröffentlichten Standes auf den Commit vor
Plan 14-08) → Deploy-Workflow abwarten und mit
`gh run list --workflow="deploy-server.yml" --limit 1` prüfen → danach Rückweg A für die
Daten → Health-Check → Funktionstest.
Den Hinweis aufnehmen, dass dieser Weg eine **Historienumschreibung auf `origin/main`** ist
und nur im Ernstfall gegangen wird; die Alternative `git revert` erzeugt bei 337 Commits keinen
sinnvoll prüfbaren Zustand.

**Abschnitt 5 — Verifikation nach dem Rückweg.** Health-Check per
`curl -s http://129.159.8.19:3000/api/health`, danach ein echter Funktionstest (Anmeldung und
Aufruf des Kontoauszugs eines Nutzers), danach `PRAGMA integrity_check` und der
Kennzahlenvergleich gegen die zurückgespielte Sicherung. Ausdrücklich vermerken, dass frische
Daten wegen WAL per direktem Dateizugriff nicht sichtbar sind und die Prüfung deshalb über die
API oder `pm2 logs` läuft.

**Abschnitt 6 — Was der Rückweg nicht zurücknimmt.** Ehrlich benennen: ein bereits
veröffentlichtes Desktop-Release (Plan 14-11) lässt sich nicht zurückziehen, sobald Anwender
es gezogen haben; deshalb liegt das Release nach der Produktionsverifikation und nicht davor
(D7). Ebenso: Zeiteinträge, die Anwender **nach** der Sicherung und **vor** dem Rückspielen
erfasst haben, gehen beim Rückweg verloren — daraus folgt die Empfehlung, das
Produktionsfenster außerhalb der Arbeitszeit zu legen und die Zeitspanne zwischen Sicherung
und Entscheidung kurz zu halten.

Setze an den Anfang des Runbooks die in Task 1 gemessenen Laufzeiten und Dateigrößen als
Erwartungswerte, damit im Ernstfall ein hängender Lauf erkennbar ist.
