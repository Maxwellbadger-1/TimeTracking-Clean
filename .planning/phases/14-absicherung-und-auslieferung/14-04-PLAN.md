## Warum das eine gefährliche Reihenfolge erzeugt

Zwei getrennte Migrationsmechanismen, verifiziert am Code:

1. `.github/workflows/deploy-server.yml:104` ruft `npm run migrate:prod` →
   `server/scripts/migrate.ts`. Dieses Skript liest **ausschließlich `.sql`-Dateien** aus
   `server/database/migrations` (`getMigrationFiles()` filtert auf `.sql`). Die
   TypeScript-Migrationen 008–015 laufen dort **nicht**.
2. `server/src/server.ts:215` ruft beim Serverstart `await runMigrations(db)` →
   `server/src/database/migrationRunner.ts`, das `server/src/database/migrations/*.ts`
   alphabetisch lädt. **Hier** laufen 008–015 — beim PM2-Start, unbeaufsichtigt.

Konsequenz für Plan 14-08: Der `git push` ist der Produktionsschreibzugriff. Es gibt keinen
Zwischenschritt, an dem der Code auf dem Server liegt, ohne dass die Migrationen laufen.

## Ein zweiter, mitzunehmender Befund

`deploy-server.yml:118` fährt `npx tsx scripts/fix-overtime.ts` **vor** dem PM2-Start, also
bevor `runMigrations()` gelaufen ist. Dieses Skript importiert
`ensureOvertimeBalanceEntries` aus `dist/services/overtimeService.js`, das über
`unifiedOvertimeService` → `getDailyTargetHours()` auf `user_work_periods` zugreift — eine
Tabelle, die zu diesem Zeitpunkt auf Produktion noch nicht existiert. Plan 14-08 behandelt
das; hier nur festhalten, damit es nicht doppelt gefunden wird.
